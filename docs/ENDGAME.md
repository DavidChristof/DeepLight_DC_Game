## 为什么现在做

> 以下为本轴启动时的背景，不是当前缺口。W20-R 已收口并归入 v0.8.0-alpha.1；最新状态见 STATUS，版本范围见 `../CHANGELOG.md`。

首局切片 W17-F、远征前哨 W18-G、拓荒者 W16-D 与生态首版已完成；目前首次击破 Boss 只设置 `state.milestone.bossDefeated`、发奖励与显示“序章完成”，随后每 7 天重复更强的 Boss。游戏能持续运行，却没有明确的胜利条件。W20-R 负责补上这个闭环，暂不重启美术重制，也不做 exe 打包。

设计继承 `DESIGN_V2.md` §8 的共鸣信标与过程式结局，但作一项必要调整：**三座信标位于地表三个不同群系，地下三层提供逐级所需的有限材料与知识**。旧蓝图要求在三个地下层各立一座、点亮后“全图蚀兽涌来”；现有标准蚀潮只在地表当前区块生成，远端有人区块仅记前线与告警。若直接照搬旧蓝图，会产生第二套离屏战斗和无限区块刷怪。W20-R 的反冲夜只改变既有标准波次的构成与目标，不创建额外波次。未来如要做地下守城，另立机制计划。

## 一局的目标链

```text
首次击破蚀巢核心
  → 获得共鸣线索与第一座信标位置
  → 远征、下潜、带回有限材料
  → 在信标所在地建立本地补给与人工光
  → 启动仪式，下一次蚀潮成为反冲夜
  → 玩家在场守住信标至黎明
  → 记录成功、解锁下一处群系信标
  → 三座共鸣 → 由本局事实生成结局 → 可读结算页
```

第一座必须单独形成可玩闭环。R3 完成后提供“首座共鸣完成”的章节结算和继续游戏入口；R5 才提供正式通关及多结局。玩家无需在第 7 天当晚完成信标，时间与远征路线保持自由。

## 核心规则与约束

### 信标地点与材料

- 三座地表信标对应藤雾林、碎岩台地、苔原，路线依次为邻近远征、深入高风险区、回营地完成共鸣。现行地图只有原点属于苔原，因此最后一座必须在营地区块内另选空位。区块目标由 `worldSeed + 坐标 + 规则版本` 确定；实际锚点从确定性基图/旧档区块的合法格中筛选，首次显露后随区块保存；未探索地点不剧透资源。
- 地点只能选可站、可建且不与既有建筑、潮穴、营地火、竖井、区块出口冲突的格。R0 的合法单格计数只是候选数量；R1/R4 要用信标的真实逻辑占地与正式建造判定复核后才锁定位置。旧档第一次生成地点时先检查已保存的区块差异，不覆盖玩家建筑；找不到合法格则延后显露、标明需要腾出的区块并报告阻塞。若占位来自可拆建筑，玩家可按现有拆除规则腾位再重试；测试夹具要覆盖这一恢复路径，不生成不可完成目标。
- 信标在地表建造和守护，材料来自现有辉髓、母髓、夜髓、燃料与研究/遗迹知识。首轮不新增“熔岩核”等尚不存在的资源。R0 用固定种子检查三处候选地的有限资源、容量和现有研究门槛，给出暂定成本与未证实的实际产出条件；R3/R4 用可玩的站点流程验证和校准。所有交付、消耗和返还走现有 `deposit/withdraw` 账本入口。
- R0 初始施工预算（逐站实测后校准）：首站信标 `{ore:12,fuel:6}`、试炼预约 `{fuel:4,night:1}`。首站本次固定回放要稳定守住信标，还实际建造了一座 `towerGlow` `{ore:6,fuel:2}`；因此当前**已验证的首站安全准备包**是 `{ore:18,fuel:12,night:1}`，不是旧表的 `{ore:12,fuel:10,night:1}`。这只是 seed 4242 本次实战的可行配置，不宣称所有种子/打法的最低成本；R4 逐站报告必需主线成本与可选防守余量。二站 `{ore:18,core:6,night:3,data:4}`、终站 `{ore:24,core:10,night:5,data:8}`仍是暂定数值，等待实战校准。失败不额外扣施工材料，信标不回滚，重试支付同一预约费。所有数字集中于 `js/data/endgame.js`，施工与预约仍须通过容器账本结算。
- 全路线预算审计同时计入三次预约：燃料共 18（首站施工 6 + 三次各 4），夜髓共 11（施工 8 + 三次各 1），施工辉髓 54；当前炼油配方 1 辉髓→2 燃料，因此燃料理论折合 9 辉髓，合计至少 63 辉髓。此数**未计**首局灯火、工具、研究、远征损耗与守潮用料，不能当成真实局通关成本。
- 固定种子审计会为每个候选区块报告确定性夜辉草点位数、第一夜理论产出上限和全点位上限。首夜按当前规则最多 6 夜髓/区块；这是所有点位均处于黑暗且可采的上界。人工光会阻止夜辉草出现，实际获取在 R3 首站和 R4 后续站点的真实昼夜流程中验证；若达不到需求，调整成本或采集顺序并重验，不能用上限宣称稳拿。
- R1 定义并展示标准净光充能所需条件；R2 实现可执行的标准充能与反冲夜。危险充能独立列为可选 R4x，三站标准主线与 R5 普通结局不依赖它；若实施，成本、收益和结局标记必须同源于数据表，启动前可见，且不绕开资源有限性与波次上限。
- 每座地点最多一个信标；不可拆建、搬运或跨区复制进行无限返还。材料不足、远端缺箱、无人工光、玩家不在场等拒绝原因必须可见。

### 反冲夜

- 启动信标只**预约下一次符合条件的地表蚀潮**。若当晚蚀潮已开始，则顺延到下一夜；同一夜只允许一个信标处于反冲试炼。入夜时一次性锁定目标信标、区块、波次主题、光压和挑战系数；存读后不得再次启动或重抽。
- 反冲夜复用 `systems/waves.js` / `data/night.js` 的波次时钟、同屏上限和敌人总量预算。它可以替换标准波次内的敌种权重、入侵前线偏好与目标优先级，**不得额外调用独立刷怪器**。Boss 周期夜若冲突，反冲夜顺延，避免两套考试叠加。
- 启动和守护期间玩家须位于目标区块。离开区块、下潜、封灯撤退、信标被毁或黎明前断光，记为试炼失败；仪式回到可重试状态，不在离屏区块继续战斗，也不凭空伤害拓荒者。被毁时保留地点身份与残骸，R2 明确维修/重建入口及其有界代价并验收，不允许出现“地点还占着、信标却永远不能修”的软锁。失败代价与重试材料由 R2 调参后集中写入数据表，必须是有限、可解释的，不允许材料复制或无限资源产出。
- 成功判定只在既有黎明边界执行一次。信标保持点燃与结构存活，试炼记录 `sealedDay/attempts/result`；成功后保留地点状态，下一座才可显露。重复存读、重复跨区、再次击破 Boss 都不能重复领奖或重复结算。
- 反冲改变玩家的布防选择：把灯、工事、拓荒者和本地补给放在远征地点，与继续守营地形成取舍。蚀痕前线仍只影响局部入口和后果，不变成第二种刷怪预算。

### 结局与继续游戏

- 三座都成功后进入正式结算。默认可继续游玩当前档；结局快照只记本局发生过的事实，不重置世界或清空存档。结局只结算一次，读档保持相同结果。
- R5 的普通结局优先级：**黎明**（至少一名未离世、未蚀化的拓荒者仍在队伍中）、**孤灯**（队伍已无人可同行，但营地/队伍曾存在）、**余辉**（旧档或无法确认队伍经历时的明确兜底）。危险充能“共生”未实现，不阻塞三站主线。一次性授予为“余辉纪念”结局记录标记，不发资源或战斗属性，避免结局奖励破坏守恒与难度。
- `DESIGN_V2.md` 的隐藏“献祭”需要拓荒者同意、永久失去与关系记忆等完整操作语义，**不在首轮自动加入**。后续另立方案，不用一个按钮换一张结局图冒充玩法。
- 结算页显示真实存活名单、墓碑数、首次击破 Boss 日、三座信标的位置与完成日、最大光压、夜采次数、蚀化/救援等**已有或可由有限事件记录得到**的指标。缺失旧档指标显示“未记录”，不能用当前值假装历史峰值。文案遵循 `docs/COPY.md`。

R3 不再把一条超长、必须连续在线且必须发生死亡的脚本当成单一验收门。每个子门都写入一份不落盘的检查点；脚本失败时从最近检查点续跑，不重打已验证的首胜，也不污染作者的三个 localStorage 键。最终仍须由同一种子的一条真实模拟状态链串起全部里程碑；检查点只是中断恢复，不得注入账本、Boss 胜利、预约或结算字段。

| 子门 | 自动执行内容 | 通过判据 | 失败时的处理 |
|---|---|---|---|
| **R3-A 供给可得 ✅** | 从首胜检查点用真实 UI/输入获得预约燃料、夜髓与实战防守物资 | 记录采集前后节点、背包/容器与账本；至少一套有限供给方案可实现 | 发现旧表漏防守塔成本，已把实战配置单列并续跑；不把这次配置称作所有打法的最低成本 |
| **R3-B 装包与施工 ✅** | 用容器 UI 手动装包，穿越区块，落地后按正常建造流程施工 | 远端付款失败不改变营地库存；明确运输后成功扣款一次；地标/建筑只出现一个，存读一致 | 已通过；该判定只覆盖首站施工，不代表预约物资或夜战供给已足 |
| **R3-C 预约状态 ✅** | 用游戏输入预约；夹具覆盖无光、资源不足和重复输入 | 拒绝无扣费；成功只扣一次并锁定唯一夜次；实测预约 `fuel 4/night 1`，重试边界由状态自检覆盖 |
| **R3-D 完整反冲夜 ✅** | 真实游戏循环推进完整普通潮夜与预约反冲夜；测试隔离随机流以固定战斗序列 | 第 9 天试炼成功；标准波次预算内、峰值同屏采样3、信标 HP140；中间普通夜死亡包真实回收；不宣称无伤通关 |
| **R3-E 章节结算 ✅** | roundtrip、重复输入及继续推进 | 结算事实仅写一次；存档恢复后仍 complete；重复 E 不重复扣资源/领奖；游戏进入第 10 天继续运行。当前通过 HUD/检查信标表达完成，不要求另造模态结算页 |

首站补给路线允许分多日准备，并可在营地/前哨存放中间物资。蚀潮开始时的远征风险仍需遵守游戏规则，但“玩家恰好死一次并完成遗落包回收”不再是 R3 的强制条件：死亡/遗落包单独由既有生存与存档回归覆盖。实际交互至少验证一次；长距离移动、等待昼夜和战斗可用自动驱动加速，但区块切换必须走会执行 `update()` 的正常帧循环，不能用只推进模拟钟的 `__steps()` 冒充移动 E2E。

**R3 完成记录（2026-09-25）**：隔离 Edge 从 seed 4242/normal 首胜检查点自动续跑，真实 UI 装包 `ore8`，在 `(1,0)` 采矿至 `ore12` 并建成信标（`ore12→0/fuel7→1`，工期 `18→0`）；返营取燃料，远端采集夜辉草 `night0→1`；实建 `towerGlow`（`ore6/fuel2`）作为防守配置；用信标真实输入预约（`fuel4/night1`），锁定下一次蚀潮。普通潮夜发生一次玩家死亡，死亡包含 `ore2`，实际交互回收后继续；第 9 天完整试炼成功，信标 `140 HP`，采样峰值同屏敌人 `3`。第 10 天重复 E 前后账本、attempts 与完成日不变。四态 `80/80`、源码 `89/89`、watch 1200 步 0 类、存档 roundtrip 保持 `complete`，三项 storage 原始字符串恢复。隔离自动化使用测试专用 seeded `Math.random` 并在结束前还原；这只固定验收随机流，生产战斗 RNG 未改。测试自动化先后遇到挖掘冷却、陈旧鼠标 hover 与帧节奏问题，均修正驱动脚本后通过，登记 D282。

### 依赖与阻塞处理

| 原先压在 R0 的事项 | 实际可验证阶段 | 处理方式 |
|---|---|---|
| 完整三站材料包、真实燃料加工与长途运输 | R3 首站、R4 后两站 | 按站点实际操作记录；每站不通过只修当前站，不拖回 R0 |
| 旧档满占格后地点延后/回退 | R1 首站、R4 后两站 | 使用可重复构造并真实存读的开发存档；R0 的只读 `blocked=true` 只证明识别能力 |
| 三站施工经济、守夜损耗与成本节奏 | R3 首站、R4 后两站、R6 全局平衡 | 建造和反冲存在后再测实付与剩余库存；初始成本不是锁死的验收常数 |
| 结局所需历史峰值与路径事实 | R2 起记录，R5 展示与判定 | 新局记录有限事件；旧档没有历史时显示“未记录”，不从当前状态伪造 |
| 右侧浏览器或开发服务临时不可用 | 每个代码阶段 | 检查当前标签和本地服务，记录一次控制错误；恢复前继续静态审计与文档工作，保留“动态未验收”。不自动使用桌面 Edge，不要求作者代测，也不把静态结果冒充通过 |

遇到失败先判断是本步代码缺陷、既有基线差异、测试夹具问题还是设计成本不成立；只把本步范围内的真实缺陷作为阶段阻塞。固定种子或真实玩家暂不可用时，使用可复现开发存档/夹具完成机器可验证部分，并明确留待试玩的问题；不把“没有试玩者”写成代码阶段无法推进的理由。开发存档已获作者授权用于测试，自动存档控制与备份是可恢复纪律，不是禁止使用存档。

自动执行采用可重复检查点：R1 使用旧档占位夹具，R2 覆盖黄昏前/开潮中/Boss 周期夜，R3 从已验证的真实首胜检查点续接 R3-A～E，R4-0 验证数据迁移；R4-A/B 每站结束各留一个内存检查点，R4-C 串联真实完成事实后再验往返，R5 从真实三站完成前检查点触发结局。检查点可以缩短等待和恢复中断，不得直接写入资源、预约、胜利或结局事实来冒充玩法验收。至少一条 R3 首站链和 R4 每个后续站点链要走实际游戏入口；路线可跨多个游戏日，不强制单次在线跑完。计划原本把通用内存检查点与驱动器基础放在 R1，但当时 R1 只有读档往返测试、没有独立无写盘导出/恢复接口；现已在 R3 补齐 `__checkpoint()` / `__restoreCheckpoint()`，并加入 `__endgameCheckpoint()`（调用真实 `runReplay`，仅在真实里程碑成功后导出）。现有 `__replay()` 的 `expedition` 策略只往返相邻区块，不能冒充远征/信标 E2E。所有夹具不引入 npm 依赖，并记录其隔离了哪些 NPC、敌人或时钟行为。每个子门失败须保留前一成功检查点和明确复跑入口，不要求从新局重走已验收路线。

## 技术落点与验证

- 数据入口：`js/data/endgame.js` 定义地点、成本、阶段和结局规则；结局统计与快照由 `js/systems/ending.js` 管理，状态写入 `js/core/state.js`、`js/core/save.js`，旧档只恢复可证实事实。
- 系统入口：`js/systems/resonance.js` 管地点、启动与黎明完成事件；`js/systems/ending.js` 记录有限指标、结局判定和旧档迁移；`js/systems/waves.js` 消费锁定的反冲计划；`js/systems/combat.js` 首次 Boss 击破时只发一次里程碑事件；`js/world/chunks.js` 管地点差异；`js/ui/screens.js` 显示结算页。以实际调用图为准，不另建重复事件总线。
- 只读观测：`__resonance()` 分阶段增长：R0 已有版本、Boss 门槛、候选区块、静态资源与预算；R1 加首座实际地点/阻塞/库存；R2 加当前与下夜试炼、锁定波次和失败原因；R4 加三站状态；R5 加结局快照。断言也随功能加入：R1 地点唯一性与旧档，R2 单夜单试炼/预算/账本/存读，R4 三站顺序与局部保存，R5 结局互斥与一次性授予。不能让尚不存在的字段或事件卡住前一阶段。
- 每个**代码交付步**完成后：右侧浏览器主菜单、新局、包含存读往返、数日回放四态 `__check()`；`__srcCheck()`；对该步新增的关键交互走一次真实键鼠；`__watch(true,20)` 后 `__testLog()` 为 0 类违例。若四态序列里的读档态已执行 `__check({roundtrip:true})`，不重复空跑。文档修订只检查计划一致性与文件差异，不空跑游戏。测试时按现有项目纪律关闭自动存档；可直接使用已获授权的开发存档，先留可恢复副本，再按测试意图保存或恢复。不能把“存档可改”误读成“绝不可用”。
- R2/R6 额外记录反冲夜与普通夜的**标准波次名额、实际生成数、峰值同屏数、光压、挑战系数**；夜潮预算和同屏上限仍来自原表。三活跃区块场景遵守单区块夜 `frame.total ≤ 8ms`、三活跃区块 `≤ 12ms`、切换首帧 `≤ 16.6ms` 的既有目标；若外部环境影响绝对值，必须同时给同机前后对照。
- 无真实玩家时，固定种子回放只能验证规则、可达性与平衡趋势；主目标是否被理解留待后续试玩观察，不阻塞 R1–R6 的机器与真实操作验收。记录具体研究问题，例如“首胜后玩家能否说出下一步”“玩家是否知道为何仪式失败”，避免只收集笼统喜好。方法参考 [Games User Research 的研究目标说明](https://gamesuserresearch.com/choose-the-right-playtest-method/)。

## 本阶段不做

- 不更换引擎，不加入 Electron/Tauri，不改逻辑格或大规模美术素材。
- 不引入经验、等级、装备词条、无限敌人、无限材料或离线战斗。
- 不同时展开天气、温度、光谱分色与复杂社交事件。它们须另立轴，并证明会改变哪一个具体决策。
- “灯网失联前哨”是完成 W20-R 后的候选 W21：复用已存在的前哨告警、救援与灯路状态，不与终局波次同批开发。
